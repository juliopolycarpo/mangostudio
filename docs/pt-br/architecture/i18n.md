# Internacionalização (i18n)

O MangoStudio usa um sistema de i18n em TypeScript puro com verificação de traduções em tempo de compilação.

## Arquitetura

```
apps/shared/src/i18n/
  pt-BR.ts    → Fonte de verdade (todas as chaves definidas aqui)
  en.ts       → Inglês do bundle inicial (tipado contra `CoreMessages`)
  en-settings.ts, en-onboarding.ts → Inglês de `settings` e `onboarding`, carregado sob demanda
  types.ts    → Tipos `Messages`, `CoreMessages`, `LoadedMessages` + união `Locale`

apps/frontend/src/lib/
  locale-dictionaries.ts → Inglês no bundle inicial; cada outro locale em um chunk próprio

apps/frontend/src/hooks/
  use-i18n.tsx → Hook de React Context sobre o dicionário carregado
```

## Convenção Das Chaves

As chaves usam notação com pontos organizada por escopo de feature:

```
auth.loginTitle
chat.input.placeholder
settings.providers.caching.title
tools.generate_image.title
```

O tipo `Messages` é inferido a partir do dicionário `pt-BR.ts` usando `as const`. Adicionar uma chave em `pt-BR` sem traduzi-la em `en.ts` gera erro de compilação porque `en.ts` é tipado como `Messages`.

## Como Funciona

### Sistema De Tipos

`types.ts` define:

```typescript
type DeepStringRecord<T> = {
  [K in keyof T]: T[K] extends string
    ? string
    : T[K] extends object
      ? DeepStringRecord<T[K]>
      : never;
};

type Messages = DeepStringRecord<typeof ptBR>;
type Locale = 'pt-BR' | 'en';
```

Isso garante que `en.ts` tenha todas as mesmas chaves de `pt-BR.ts`, embora os valores possam ser strings diferentes.

### Hook React

`useI18n()` retorna `{ t, locale, setLocale }`:

```tsx
import { useI18n } from '@/hooks/use-i18n';

function MyComponent() {
  const { t } = useI18n();
  return <h1>{t.auth.loginTitle}</h1>;
}
```

- **Detecção de locale:** verifica primeiro `localStorage` (`mangostudio:locale`), depois `navigator.language`; o padrão é `en`.
- **Lazy loading:** o inglês (menos os namespaces adiados abaixo) vai no chunk inicial e é o fallback. Cada outro locale é um chunk
  próprio, importado pelo subpath `@mangostudio/shared/i18n/<locale>` em
  `lib/locale-dictionaries.ts`. `main.tsx` começa a carregar o locale inicial antes do primeiro
  render, junto com a requisição de sessão. Uma troca em runtime mantém o texto atual até o próximo
  dicionário chegar; uma falha de carregamento renderiza inglês e mantém a escolha salva para a
  próxima inicialização.
- **Persistência:** `setLocale()` atualiza o estado React e o `localStorage`.

### Namespaces adiados

`settings` e `onboarding` somam cerca de 9 KB em Brotli do dicionário em inglês e não são lidos
antes da primeira pintura da rota de chat, então ficam fora do chunk inicial. `en.ts` é tipado
`CoreMessages` (`Messages` sem esses dois); `en-settings.ts` e `en-onboarding.ts` guardam um
namespace cada e carregam como chunk próprio. O português continua um único chunk lazy com todos
os namespaces, sem segunda requisição.

Quem lê um deles o nomeia: `useI18n('settings')` devolve `t` tipado como `CoreMessages` mais
`settings`. `useI18n()` devolve só `CoreMessages`, então `t.settings.*` sem nomear o namespace é
erro de compilação, nunca uma leitura `undefined` em runtime
(`tests/unit/hooks/use-i18n-deferred.test.tsx` fixa isso com um `@ts-expect-error`). Um helper que
recebe o dicionário tipa o parâmetro como `CoreMessages`, ou `LoadedMessages<'settings'>` quando
lê um namespace adiado.

O namespace já deve estar carregado quando o componente renderiza. A rota dona da tela o carrega no
`loader` com `preloadNamespaces(['settings'])`, que o TanStack executa junto com o componente lazy
da rota (`settings.tsx` para todas as páginas de `/settings`, `welcome.tsx` para o fluxo de
configuração, `settings/general.tsx` para o cartão de configuração dessa página e o chunk lazy da
paleta de comandos). `preloadNamespaces` cobre o dicionário que o provider mostra e também o
locale salvo: após uma falha do chunk `pt-BR` na inicialização, o inglês fica na tela enquanto
`pt-BR` continua salvo. Se um componente renderizar antes disso, `useI18n` suspende até o namespace
chegar; por isso ele precisa estar sob um Suspense com fallback escolhido de propósito (o da
paleta não renderiza nada). Um chunk que não pode ser buscado lança para o error boundary mais
próximo; o store repete essa falha por um segundo para que o novo render do React não inicie uma
busca a cada passada.

Trocar de locale em uma tela que lê um namespace que o novo locale ainda não carregou (português
para inglês, quando o `settings` em inglês nunca foi necessário) acontece em uma transição: o
texto antigo fica na tela até o namespace chegar, sem piscar o fallback.

**Regra da primeira pintura.** Tudo que a rota de chat, a barra lateral, o cabeçalho ou outra
superfície que renderiza antes dessas rotas lê deve vir de um namespace do bundle inicial. O
rótulo do atalho de configurações é `common.settings` e os toasts de falha do autosave são
`errors.settingsSaveFailed` e `errors.settingsSaveReverted` por esse motivo.
`tests/unit/components/first-paint-deferred-namespaces.test.tsx` renderiza a superfície do chat com
chunks adiados que nunca chegam.

Para adiar outro namespace, adicione-o a `DeferredNamespace` em `types.ts`, separe seu inglês em
`en-<nome>.ts` com um export de subpath `./i18n/en-<nome>`, adicione o loader em
`eagerNamespaces` em `lib/locale-dictionaries.ts`, estenda as entradas `no-restricted-imports` em
`bunfig.toml` e carregue-o na rota dona.

### Provider

`I18nProvider` envolve a raiz da aplicação e fornece o contexto de i18n:

```tsx
<I18nProvider>
  <App />
</I18nProvider>
```

Usa a API `use()` do React 19 para consumo do contexto. Lança erro se `useI18n()` for chamado fora do provider.

## Adicionando Um Novo Idioma

1. Crie o arquivo do dicionário, por exemplo `apps/shared/src/i18n/es.ts`.
2. Copie a estrutura de chaves de `pt-BR.ts` e traduza todos os valores.
3. Tipa o arquivo como `Messages` para garantir compatibilidade estrutural:

   ```typescript
   import type { Messages } from './types';
   export const messages: Messages = {
     /* traduções */
   };
   ```

4. Adicione o locale ao tipo `Locale` em `types.ts`:

   ```typescript
   type Locale = 'pt-BR' | 'en' | 'es';
   ```

5. Conecte o lazy loading: um subpath export `./i18n/es` em `apps/shared/package.json`, um loader
   em `apps/frontend/src/lib/locale-dictionaries.ts`, um ramo em `detectLocale()` e uma entrada
   `no-restricted-imports` para o subpath em `bunfig.toml`. Módulos de shared importam um dicionário
   do próprio arquivo, nunca um valor em runtime do barrel `i18n`, ou todos os dicionários vão
   para o chunk inicial.
6. Adicione a opção de locale na UI de appearance settings, se fizer sentido.

## Adicionando Novas Chaves

1. Adicione a chave em `pt-BR.ts` na seção apropriada.
2. Adicione a tradução em `en.ts` no mesmo caminho. Se você esquecer esse passo, o build falhará porque `en.ts` precisa satisfazer o tipo `Messages`.
3. Use a chave via `t.path.to.key` nos componentes.

| Locale  | Cobertura                   | Arquivo    |
| ------- | --------------------------- | ---------- |
| `pt-BR` | Completa (fonte de verdade) | `pt-BR.ts` |
| `en`    | Completa                    | `en.ts`    |

## Seções Das Chaves

Exemplos de seções de topo, sem pretensão de inventário completo. Os dicionários
e o tipo `Messages` acima definem a cobertura atual de chaves:

- `auth` — login, signup e mensagens de erro
- `chat` — UI do chat, barra de input, feed, contexto, continuação e eventos de sistema
- `studio` — workspace de imagem
- `gallery` — página da galeria
- `settings` — tabs, contexto, prompts, general, connectors, providers, tools e appearance
- `common` — rótulos compartilhados, como salvar, cancelar, deletar e confirmar
- `providers` — nomes de exibição e descrições de provedores
- `thinking` — rótulos de thinking/reasoning
- `tools` — nomes de tools, categorias e labels de parâmetros
- `errors` — mensagens de erro
- `api` — mensagens de status da API
- `generation` — rótulos relacionados à geração
