# Internationalization (i18n)

MangoStudio uses a pure TypeScript i18n system with compile-time translation verification.

## Architecture

```
apps/shared/src/i18n/
  pt-BR.ts    → Source of truth (all keys defined here)
  en.ts       → Eager English translations (typed against CoreMessages)
  en-settings.ts, en-onboarding.ts → English `settings` and `onboarding`, loaded on demand
  en-environments.ts, en-git.ts, en-github.ts, en-library.ts → the rest of those four namespaces,
                imported by the feature's lazy chunk
  types.ts    → Messages, CoreMessages, LoadedMessages types + Locale union

apps/frontend/src/lib/
  locale-dictionaries.ts → English eager, every other locale loaded as its own chunk

apps/frontend/src/hooks/
  use-i18n.tsx → React Context hook over the loaded dictionary
```

## Key Convention

Keys use dot-separated notation organized by feature scope:

```
auth.loginTitle
chat.input.placeholder
settings.providers.caching.title
tools.generate_image.title
```

The `Messages` type is inferred from the `pt-BR.ts` dictionary using `as const`. Adding a key to `pt-BR` without translating it in `en.ts` is a compile-time error because `en.ts` is typed as `Messages`.

## How It Works

### Type System

`types.ts` defines:

```typescript
type DeepStringRecord<T> = {
  [K in keyof T]: T[K] extends string
    ? string
    : T[K] extends object
      ? DeepStringRecord<T[K]>
      : never;
};

type Messages = DeepStringRecord<typeof ptBR>;
type Locale = 'pt-BR' | 'en';
```

This ensures that `en.ts` must have all the same keys as `pt-BR.ts` but values can be different strings.

### React Hook

`useI18n()` returns `{ t, locale, setLocale }`:

```tsx
import { useI18n } from '@/hooks/use-i18n';

function MyComponent() {
  const { t } = useI18n();
  return <h1>{t.auth.loginTitle}</h1>;
}
```

- **Locale detection:** Checks `localStorage` (`mangostudio:locale`) first, then `navigator.language`, defaults to `en`.
- **Lazy loading:** English (minus the deferred namespaces below) is bundled in the entry chunk and is the fallback. Every other locale
  is its own chunk, imported through its `@mangostudio/shared/i18n/<locale>` subpath by
  `lib/locale-dictionaries.ts`. `main.tsx` starts loading the startup locale before the first
  render, alongside the session request. A runtime switch keeps the current text until the next
  dictionary arrives; a failed load renders English and keeps the stored choice for the next start.
- **Persistence:** `setLocale()` updates both React state and `localStorage`.

### Deferred namespaces

`settings` and `onboarding` are about 9 KB Brotli of the English dictionary and are not read before
the first paint of the chat route, so they are not in the entry chunk. `en.ts` is typed
`CoreMessages` (`Messages` without those two); `en-settings.ts` and `en-onboarding.ts` each hold
one namespace and load as their own chunk. Portuguese stays one lazy chunk that carries every
namespace, so it needs no second request.

A component that reads one names it: `useI18n('settings')` returns `t` typed as `CoreMessages`
plus `settings`. `useI18n()` returns `CoreMessages` only, so `t.settings.*` without naming the
namespace is a compile error, never an `undefined` read at runtime
(`tests/unit/hooks/use-i18n-deferred.test.tsx` pins this with a `@ts-expect-error`). A helper that
takes the dictionary types the parameter `CoreMessages`, or `LoadedMessages<'settings'>` when it
reads a deferred namespace.

The namespace should already be loaded when the component renders. The route that owns the
screen loads it in its `loader` with `preloadNamespaces(['settings'])`, which TanStack runs next
to the route's lazy component (`settings.tsx` for every page under `/settings`, `welcome.tsx`
for the setup flow, `settings/general.tsx` for the setup card on that page, and the command
palette's lazy chunk). `preloadNamespaces` covers the dictionary the provider shows as well as the
saved locale: after a failed `pt-BR` chunk at startup, English is on screen while `pt-BR` stays
saved. If a component renders before that, `useI18n` suspends until the
namespace arrives, so it must sit under a Suspense boundary whose fallback is chosen on purpose
(the palette's renders nothing). A chunk that cannot be fetched throws to the nearest error
boundary; the store replays that failure for one second so React's re-render does not start a
new fetch on every pass.

Switching locale on a screen that reads a namespace the new locale has not loaded (Portuguese to
English, when English `settings` was never needed) happens in a transition: the old text stays on
screen until the namespace arrives, with no fallback flash.

**First-paint rule.** Anything the chat route, the sidebar, the header or another surface that
renders before those routes reads must come from an eager namespace. The settings shortcut label
is `common.settings` and the autosave failure toasts are `errors.settingsSaveFailed` and
`errors.settingsSaveReverted` for this reason. `tests/unit/components/first-paint-deferred-namespaces.test.tsx`
renders the chat surface with deferred chunks that never arrive.

To defer another namespace, add it to `DeferredNamespace` in `types.ts`, split its English into
`en-<name>.ts` with a `./i18n/en-<name>` subpath export, add the loader to `eagerNamespaces` in
`lib/locale-dictionaries.ts`, extend the `no-restricted-imports` entries in `bunfig.toml`, and
load it from the owning route.

### Feature namespaces

`environments`, `git`, `github` and `library` are big (about 10 KB Brotli together outside the keys
the first paint reads) and mostly read inside one lazy chunk, but a few of their keys are read
elsewhere (the sidebar, the command palette, the home widgets, the chat feed). They are split by
key instead of loaded as a unit. `EagerFeatureKeys` in `types.ts` lists the keys that stay in
`en.ts`; every other key of the namespace is in `en-<name>.ts`. `CoreMessages` has only the eager
keys of these namespaces, so a read of any other key outside the feature is a compile error.

The feature's own components pass the rest as a value: `features/library/library-i18n.ts`
re-exports `en-library` as `libraryMessages`, and a component in the Library chunk calls
`useI18n(libraryMessages)`. The module is imported statically from the chunk, so the strings are
bundled into it and arrive in the same request round as the code that reads them: no loader, no
Suspense and no extra round trip. `withFeatureMessages` merges the keys into the English
dictionary; a dictionary that already carries them (Portuguese, which is one chunk with every
key) is returned as is, so the English text never overwrites a translation. The result is cached
per pair, so it is safe in a dependency list. `useI18n` takes both kinds of argument:
`useI18n('settings', libraryMessages)`.

When a new component outside the feature's chunk needs a key, add that key to `EagerFeatureKeys`
and move it from `en-<name>.ts` to `en.ts`; importing the feature module from there instead would
put the whole file back in the entry chunk. `tests/unit/i18n-feature-namespaces.test.ts` walks the
static imports from `main.tsx` and fails on that import, and the first-paint test renders the chat
surface over the real `en.ts`.

To split another namespace, add it to `EagerFeatureKeys`, move its non-eager keys to
`en-<name>.ts` typed `FeatureMessages<'<name>'>` (join it in `en` in `i18n/index.ts`), add the
subpath export, the `no-restricted-imports` entry and the plumbing file to `bunfig.toml`, and add
`<feature>-i18n.ts` next to the feature.

### Provider

`I18nProvider` wraps the app root and provides the i18n context:

```tsx
<I18nProvider>
  <App />
</I18nProvider>
```

Uses React 19's `use()` API for context consumption. Throws if `useI18n()` is called outside the provider.

## Adding a New Language

1. Create the dictionary file (e.g., `apps/shared/src/i18n/es.ts`).
2. Copy the key structure from `pt-BR.ts` and translate all values.
3. Type the file as `Messages` to ensure structural compatibility:
   ```typescript
   import type { Messages } from './types';
   export const messages: Messages = {
     /* translations */
   };
   ```
4. Add the locale to the `Locale` type in `types.ts`:
   ```typescript
   type Locale = 'pt-BR' | 'en' | 'es';
   ```
5. Wire the lazy loading: a `./i18n/es` subpath export in `apps/shared/package.json`, a loader in
   `apps/frontend/src/lib/locale-dictionaries.ts`, a branch in its `detectLocale()`, and a
   `no-restricted-imports` entry for the subpath in `bunfig.toml`. Shared modules import a dictionary
   from its own file, never a runtime value from the `i18n` barrel, or every dictionary lands in
   the entry chunk.
6. Add the locale option in the appearance settings UI if desired.

## Adding New Keys

1. Add the key to `pt-BR.ts` in the appropriate section.
2. Add the translation to `en.ts` in the same path. If you miss this step, the build will fail because `en.ts` must satisfy the `Messages` type.
3. Use the key via `t.path.to.key` in components.

## Key Sections

Examples of top-level sections follow; this is not an exhaustive inventory. The dictionaries
and the `Messages` type above define current key coverage:

- `auth` — Login, signup, error messages
- `chat` — Chat UI, input bar, feed, context, continuation, system events
- `studio` — Image workspace
- `gallery` — Gallery page
- `settings` — Tabs, context, prompts, general, connectors, providers, tools, appearance
- `common` — Shared labels (save, cancel, delete, confirm)
- `providers` — Provider display names and descriptions
- `thinking` — Thinking/reasoning labels
- `tools` — Tool names, categories, parameter labels
- `errors` — Error messages
- `api` — API status messages
- `generation` — Generation-related labels
