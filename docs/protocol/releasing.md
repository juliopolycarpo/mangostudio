# Releasing

One git tag releases both packages: `@mangostudio/protocol` to npm and `mango-protocol` to
crates.io, with the schema files attached to a GitHub release. The tag is the only trigger; no
token is stored in the repository or in CI.

The Mango Protocol shares this repository with the MangoStudio application but not its release
train. Protocol tags are prefixed `protocol-v`; the bare `v*` tags belong to the application and
fire `.github/workflows/release.yml`, which is anchored so it can never see a protocol tag. The
version lines move independently — the root `package.json` version is the application's and is
deliberately not one of the manifests below.

|             | Protocol                                 | Application                     |
| ----------- | ---------------------------------------- | ------------------------------- |
| Tag         | `protocol-v0.2.1`                        | `v0.2.1`                        |
| Workflow    | `.github/workflows/protocol-release.yml` | `.github/workflows/release.yml` |
| Environment | `protocol-release`                       | `release`                       |
| Changelog   | `packages/protocol/CHANGELOG.md`         | `CHANGELOG.md`                  |
| Prepare     | `bun run protocol:release:prepare`       | `bun run release:prepare`       |

## Cut a release

1. Make sure `main` is green, including the half the repository gate does not run:

   ```sh
   bun run protocol:check && bun run protocol:test
   ```

2. Move every protocol manifest to the new version. The script rewrites
   `packages/protocol/package.json` and the Cargo workspace version, refreshes `Cargo.lock`, and
   **prepends** the new section to `packages/protocol/CHANGELOG.md`. It runs on a maintainer's
   machine, not in CI.

   ```sh
   bun run protocol:release:prepare 0.2.1
   ```

3. Review the diff and merge the release preparation through a pull request. After it lands,
   tag the commit on `main`. The workflow verifies that the exact tag exists and its commit is
   reachable from `origin/main`; a commit from the preparation branch that was rewritten by a
   squash merge will be refused. The release procedure uses a signed tag, but the workflow does
   not verify the tag signature.

   ```sh
   git switch main
   git pull --ff-only origin main
   bun ./scripts/protocol/check-versions.ts 0.2.1
   git tag -s protocol-v0.2.1 -m "protocol-v0.2.1"
   git push origin protocol-v0.2.1
   ```

   To retry through `workflow_dispatch`, select the same `protocol-v0.2.1` tag as the ref
   and supply `0.2.1` as the version. Dispatching from a branch is refused.

4. Watch the `Protocol Release` workflow. It verifies the manifests match the tag, runs
   `bun run protocol:check` and `bun run protocol:test`, proves the published tarball with
   `bun run protocol:verify-package`, publishes to npm, publishes to crates.io, and creates the
   GitHub release with `spec/schema/1/*.json` attached.

The version is one number across three manifests — `packages/protocol/package.json`, the root
`Cargo.toml` `[workspace.package]` version, and `Cargo.lock`. `bun run protocol:check` fails when
any of them drifts, and the workflow refuses a tag whose manifests disagree with it.

## Packing: why publishing never happens from `packages/protocol`

The workspace resolves this package from `src/`, like every other workspace here — nothing in the
Turbo graph builds `dist/` before a typecheck or a test lane, so a `dist`-pointing workspace link
is unresolvable on a clean checkout. The published map therefore lives in `publishConfig.exports`
and points at `dist/`.

**npm does not apply it.** Measured on npm 11.19.0: `npm pack` copies `publishConfig` into the
tarball verbatim and leaves `exports` alone. A tarball packed from `packages/protocol` installs
with an `exports` map pointing at `src/`, which `files` does not ship, and every import fails with
`Cannot find module '@mangostudio/protocol'`.

So `bun run protocol:pack` stages the package into `.mango/out/protocol/package` with the
published manifest written out — `exports` replaced, `publishConfig` stripped of its copy, and
`scripts` dropped — and packs there. `protocol-release.yml` publishes from that directory.
`bun run protocol:verify-package` packs, installs the tarball into a throwaway project and imports
every published subpath; it is the only thing in the repository that exercises the published
`files`/`exports`, and it runs in the release workflow's verify job and on every protocol pull
request.

## Changelog conventions

`packages/protocol/CHANGELOG.md` is generated by git-cliff from Conventional Commits and never
hand-edited; `packages/protocol/cliff.toml` maps each commit type to one changelog section. A
pre-release fix — a fix to something that has not shipped in a release yet — may still appear
under "Bug Fixes": the commit type follows the artefact being changed, not the release state of
the thing it fixes.

The file is **prepended to, never regenerated**. Its 0.1.0 and 0.2.0 sections were generated in
`juliopolycarpo/mango-protocol` before the tree moved here, and those commits carry the upstream
tree's root-relative paths, which this repository's own directories now occupy — regenerating
returns 70 of the 87 entries and loses the 0.1.0 release boundary entirely. The note at the bottom
of `packages/protocol/cliff.toml` has the measurements.

## Pre-releases

A pre-release tag (`protocol-v0.2.1-rc.1`) publishes to npm under the `next` dist-tag and to
crates.io as a pre-release version; Cargo does not resolve it from a caret requirement. The GitHub
release is created with `--prerelease`, so it never becomes the repository's latest.

## What the workflow needs

The repository owner sets these up once.

- A GitHub environment named `protocol-release` whose deployment branch rule admits only tags
  matching `protocol-v*`. The publish jobs run in it, so a push to a branch can never publish.
  Deliberately not the application's `release` environment, which holds the Homebrew tap and Scoop
  bucket tokens this train has no business reaching.
- npm trusted publishing for `@mangostudio/protocol`, in the package settings on npmjs.com: owner
  `juliopolycarpo`, repository `mangostudio`, workflow filename `protocol-release.yml`, environment
  `protocol-release`. The allowed actions must include **`npm publish`** — a configuration created
  after 2026-09-03 permits only `npm stage publish` by default, and the publish step runs
  `npm publish --provenance --access public` with the OIDC token GitHub mints for the job.
- crates.io trusted publishing for `mango-protocol`, in the crate settings on crates.io, with the
  same four values. The environment field is filled here, unlike the application crate on
  `release.yml`, because the `crate` job declares `environment: protocol-release`. The publish step
  uses `rust-lang/crates-io-auth-action` to exchange the OIDC token for a short-lived one.

Trusted publishing binds a repository, a workflow filename and an environment name. All three
changed when the tree moved here, so both registries were repointed on 2026-09-16. Adding a
publisher does not replace the old one — npm allows up to ten per package, crates.io several — so
the `juliopolycarpo/mango-protocol` configurations are still live and remain the fallback until a
release from this repository succeeds. They are deleted with the archive step, not before, and
crates.io's "Require trusted publishing for all new versions" stays off for a related but distinct
reason: it would block the token/manual fallback used for the hand-published first version below,
and that fallback stays available until a release from this repository succeeds.

Neither registry lets a name that does not exist yet be configured, so this is the recipe for a
future rename, not for today: both `@mangostudio/protocol` and `mango-protocol` exist and are
configured. A first version published by hand goes through the staging directory for the reason
above:

```sh
bun run protocol:pack
cd .mango/out/protocol/package && npm login && npm publish --access public
cd - && cargo login && cargo publish -p mango-protocol --locked
```

Configuring trusted publishing then lets the workflow handle every later tag, with no long-lived
token stored anywhere. The tag for that hand-published version can still be pushed: each publish
job checks its registry before asking for a token, skips a version that is already there, and the
GitHub release is created as usual.

## Schema files

Every release attaches `protocol.json` and `catalog.json` from `spec/schema/1/`. The same files
are published in the npm package under `@mangostudio/protocol/schema/1/*.json` — a published-only
subpath: `build.ts` copies them out of `spec/` into a gitignored `packages/protocol/schema/`, and
in-repo readers take `spec/schema/1/` directly. They are meant to be served at
`https://mangostudio.dev/protocol/schema/1/`, the `$id` they declare. The Rust crate does not embed
the schema files; its `schema` feature emits an equivalent document at runtime.

## When a release fails

`verify` runs first; `npm` and `crate` then run **concurrently**, and `github-release` waits for
both. So a failure in either publish job says nothing about the other — an npm failure can still
leave `mango-protocol` on crates.io, and vice versa. Check both registries before deciding what is
left to do.

Each publish job skips a version already on its registry. A published GitHub release is
immutable, so a rerun skips it without uploading assets again. Fix the cause and rerun the
failed jobs.

A failed release creation can leave a draft with incomplete assets. The workflow refuses that
draft; delete only the draft, preserve the tag, then rerun the failed job:

```sh
gh release delete protocol-v0.2.1 --cleanup-tag=false
```

Never delete or move a tag that published anything. If the release needs code changes, merge
them through a new release preparation pull request and cut the next patch.
