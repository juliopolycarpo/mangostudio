# Releasing

One git tag releases both packages: `@mangostudio/protocol` to npm and `mango-protocol` to
crates.io, with the schema files attached to a GitHub release. The tag is the only trigger; no
token is stored in the repository or in CI.

## Cut a release

1. Make sure `main` is green and the changelog preview reads well:

   ```sh
   bun run changelog
   git diff CHANGELOG.md
   ```

2. Move every manifest to the new version. The script rewrites `package.json`,
   `packages/protocol/package.json` and the Cargo workspace version, refreshes `Cargo.lock`
   and regenerates `CHANGELOG.md` with the new tag applied to the unreleased commits. It runs
   on a maintainer's machine, not in CI.

   ```sh
   bun run release:prepare 0.2.0
   ```

3. Review the diff, commit, tag and push. The tag must be signed.

   ```sh
   git add -A && git commit -m "chore(release): v0.2.0"
   git tag -s v0.2.0 -m "v0.2.0"
   git push origin main v0.2.0
   ```

4. Watch the `Release` workflow. It verifies the manifests match the tag, runs `bun run check`
   and `bun run test`, builds the package, publishes to npm, publishes to crates.io, and
   creates the GitHub release with `spec/schema/1/*.json` attached.

The version is one number everywhere. `bun run check` fails when any manifest drifts, and the
workflow refuses a tag whose manifests disagree with it.

## Changelog conventions

`CHANGELOG.md` is generated by git-cliff from Conventional Commits (`bun run changelog`) and is
never hand-edited; `cliff.toml` maps each commit type to one changelog section. A pre-release fix
— a fix to something that has not shipped in a release yet — may still appear under "Bug Fixes"
in the generated changelog: the commit type follows the artefact being changed, not the release
state of the thing it fixes.

## Pre-releases

A pre-release tag (`v0.2.0-rc.1`) publishes to npm under the `next` dist-tag and to crates.io
as a pre-release version; Cargo does not resolve it from a caret requirement. Canary tags
(`v*-canary*`) are ignored by the workflow.

## What the workflow needs

The repository owner sets these up once.

- A GitHub environment named `release` whose deployment branch rule admits only tags matching
  `v*`. The publish jobs run in it, so a push to a branch can never publish.
- npm trusted publishing for `@mangostudio/protocol`, configured in the package settings on
  npmjs.com with this repository and the workflow file `release.yml`. The publish step runs
  `npm publish --provenance --access public` with the OIDC token GitHub mints for the job.
- crates.io trusted publishing for `mango-protocol`, configured in the crate settings on
  crates.io with this repository and the same workflow file. The publish step uses
  `rust-lang/crates-io-auth-action` to exchange the OIDC token for a short-lived one.

Trusted publishing can only be configured for a package that already exists. The first
version of each package is therefore published from a maintainer's machine:

```sh
cd packages/protocol && bun run build && npm login && npm publish --access public
cd ../../crates/mango-protocol && cargo login && cargo publish
```

After that, configure trusted publishing in both registries and let the workflow handle
every later tag. No long-lived token is stored anywhere. The tag for that first version can
still be pushed: each publish job checks its registry before asking for a token, skips a
version that is already there, and the GitHub release is created as usual.

## Schema files

Every release attaches `protocol.json` and `catalog.json` from `spec/schema/1/`. The same
files are published in the npm package under `@mangostudio/protocol/schema/1/*.json` and are
meant to be served at `https://mangostudio.dev/protocol/schema/1/`, the `$id` they declare.
The Rust crate does not embed the schema files; its `schema` feature emits an equivalent
document at runtime.

## When a release fails

The jobs run in order: verify, npm, crates.io, GitHub release. A failure in the npm job leaves
nothing published. A failure in the crates.io job leaves the npm version published; fix the
cause and re-run the workflow from the failed job (each publish job skips a version that is
already on its registry). Never delete a tag that published anything; cut the next patch.
